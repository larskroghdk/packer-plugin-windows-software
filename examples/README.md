# Run the Windows software example

`Invoke-PackerExample.ps1` runs the existing [windows-software.pkr.hcl](windows-software.pkr.hcl). It does not create a VM: the `null` builder provisions an existing **disposable Windows VM** over WinRM TLS and installs all five configured packages.

## Prerequisites

- PowerShell 7.4 or newer (`pwsh`).
- Packer on `PATH` (the repository documents Packer 1.11 or newer).
- Go on `PATH`, with the toolchain version specified in `../go.mod` available.
- Network access for Go dependencies and the installer sources recorded in `../packages/catalog.json`.
- A disposable x64 Windows VM supported by the package catalog, with WinRM HTTPS reachable from the Packer host. Its certificate must be trusted and match the connection hostname. Use an elevated guest account.

The runner preserves the HCL example's WinRM TLS settings. It does not change the VM's connection configuration or issue restarts. Installation may require a later, separately managed reboot.

## Default execution

From the repository root:

```powershell
./examples/Invoke-PackerExample.ps1
```

When no variable file is selected, the script prompts for missing `winrm_host`, `winrm_username` and `winrm_password`. The password prompt uses `SecureString`. Existing `PKR_VAR_` environment variables satisfy the corresponding prompts.

The runner works from other directories too; the script resolves the template from its own location and runs Packer from the repository root. The existing catalog and report paths therefore keep their meaning.

## Custom variables

```powershell
$connection = @{
    winrm_host     = 'template-test.example.test'
    winrm_username = 'Administrator'
    winrm_password = Read-Host 'Disposable VM password' -AsSecureString
    catalog_path   = 'packages/catalog.json'
}
./examples/Invoke-PackerExample.ps1 -Variables $connection -NonInteractive -Verbose
```

`Variables` accepts the existing example's scalar variables. Values are placed in child-process `PKR_VAR_` environment variables, not command-line arguments. They override inherited variables with the same names. No changes are made to the parent session's environment.

For unattended use, supply all required variables and pass `-NonInteractive`. Missing inputs then fail Packer validation rather than prompting.

## Variable files

```powershell
./examples/Invoke-PackerExample.ps1 -VariableFile ./private/windows.pkrvars.hcl
./examples/Invoke-PackerExample.ps1 -VariableFile ./base.pkrvars.hcl, ./private/override.pkrvars.hcl
```

Relative variable-file paths are resolved from the caller's working directory. Files are passed to both validation and build, in the supplied order; later files override earlier files and file values override `PKR_VAR_` values. When `-VariableFile` is omitted, the runner uses `examples/windows-software.pkrvars.hcl` if present. With a file selected, it does not prompt; provide any missing inputs through `Variables` or environment variables.

Keep credential files private and untracked. The default `examples/windows-software.pkrvars.hcl` is ignored by Git. No variable file or duplicate Packer configuration is generated by the runner.

## Local plugin preparation

Every invocation runs `go build`; Go's build cache avoids recompiling unchanged dependencies. The build uses the host architecture and clears the development prerelease suffix so the binary satisfies the example's existing stable version constraint. It retains the version defined by the project.

The runner installs the binary with `packer plugins install -path` into a unique directory under `.cache/packer-example/`, exposed only to child processes through `PACKER_PLUGIN_PATH`. Your normal plugin installation is untouched. It then runs:

1. `packer init` against the existing HCL file.
2. `packer plugins required`, requiring exactly one installed windows-software binary whose hash matches the local build and whose path is selected by the example.
3. `packer validate` with the selected variable files.
4. `packer build` with those same variable files.

The isolated directory prevents a previously published plugin from taking precedence. Files remain in the ignored cache for inspection; repeated runs create additional isolated directories.

See HashiCorp's [local plugin installation](https://developer.hashicorp.com/packer/docs/plugins/install) and [plugin path configuration](https://developer.hashicorp.com/packer/docs/configure) documentation for the underlying workflow.

## Validation without provisioning

```powershell
./examples/Invoke-PackerExample.ps1 -Variables $connection -NonInteractive -ValidateOnly
```

This still builds, installs, initializes and validates the local plugin, but does not run `packer build` or connect to the VM. Successful validation does not certify live installation or WinRM connectivity.

## Logging and failures

Start time, end time, elapsed duration, current stage and final status are displayed. `-Verbose` and `-Debug` add runner diagnostics without printing variable values or native command arguments. They do not enable Packer's interactive `-debug` mode.

Native stdout/stderr is withheld and inherited `PACKER_LOG`/`PACKER_LOG_PATH` settings are removed from child processes to prevent diagnostic output from exposing credentials. Native output is not saved to a log file. On failure, the runner identifies the failed stage and gives suggested checks. For provisioning failures, inspect `reports/windows-software.json` when available; treat it as potentially sensitive operational data.

The script stops at the first failed stage and returns that native command's exit code. Runner/dependency errors return 1; successful execution or validation-only execution returns 0. In PowerShell, inspect `$LASTEXITCODE`. A failed or timed-out installation VM should be discarded before retrying.
